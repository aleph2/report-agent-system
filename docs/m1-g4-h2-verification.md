# G4 H2 — prepared planning data and step tools

H2 implements the approved G4 repair plan and the owner's H1 review additions.
It closes the remaining capability-choice escape: a new planning contract uses
source-bound reviewed classifications independently of the Coordinator's proposed
statuses. An unlinked required convention cannot evade its method/table obligations.

## Delivered behavior

- Host preparation installs reviewed entries and classifications against exact
  source hashes, anchor locations and quote hashes. The Coordinator selects an
  eligible entry ID; the system derives capabilities and attaches the canonical
  method, weight strategy and table specifications. Ordinary requirements retain
  their meaning without being forced into non-applicability. Unknown classifications
  require an explicit owner resolution.
- Independent step tools save requirements, links, objects, sections, boundaries,
  substitutions, reconciliations and questions in any order. Stable IDs permit
  revisions. Final submission returns the combined missing/invalid-item list and
  still requires the existing owner plan confirmation. The brief describes the
  convention-to-source result in readable language.
- Fixed sections use template pages and unique start/end sentences. The system
  extracts text and applies a small source-bound normalization profile. Raw
  citations, selected endpoints and normalization proof remain available and are
  revalidated at authority boundaries. Existing replacements, result bindings and
  source image views remain supported.
- Parse/classification decisions use a version-bound owner reply with a written
  note. The original error and evidence remain recorded; this decision grants no
  writing authority. Generated Markdown/JSON sidecars expose the exact reply shape
  and eligible entries. Native replay reuses the original checkpoint receipt.
- Five consecutive rejected planning writes create a persistent human wait.
  Invalid JSON, schema and business failures count once by native call ID. Reads,
  no-op replay and successful siblings cannot clear a latched wait. The guard runs
  before model/summary work and inside the Coordinator's serial tool lock, blocking
  queued helpers after the fifth rejection. Only the typed owner reply resumes it.

The existing scope layout and configured outline filename are documented in
[pilot-inputs.md](pilot-inputs.md). Report-specific classifications, entry labels,
weight selection and extraction profile are data in `methods/pilot_planning.json`;
runtime discovery for new reports remains outside H2.

## Limits and next gate

The regression uses scripted models and network-disabled fresh cases with the
existing old-input Python audit fence. The fence is not an OS sandbox and retains
its documented fd-relative-operation limitation. The separate original-source audit
is explicitly bounded read-only input work, not part of the synthetic input fence.
No old case or financial database was opened and no provider call was made.

The summary spy proves middleware ordering, not real-provider compaction. The guard
blocks queued admission; it does not cancel work that already started. The PDF audit
covers one selected section and is not full-template crop/layout validation.

H3 retains real-attempt replay, inventory/access-coverage evidence, the complete
scripted calculation/export pass and full-suite testing. Autonomous behavior,
engineering inventory and engineering sign-off remain unverified. H2 owner review
precedes H3; a new paid report run still requires separate authorization. The owner
authorized one completion email; inbox polling and scheduled progress remain stopped.
