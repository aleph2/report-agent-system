# 对象审核状态实现 v1.2

2026-09-30；承接分层审核修复 v1.1。实现目标是让智能体看见某个精确版本有哪些审核结论、尚未执行什么、哪些历史结果需要判断适用性。

## 职责与数据

协调者负责验收目标和范围及后续行动。审核者负责明确范围内的语义判断、调查策略和证据充分性。代码保留这些判断及其版本边界，不从几个局部 S 推断整个节点或文档 S。审核者声明的“whole node”等范围原样保存在 `scopes`；对象摘要不会替审核者扩大范围，也不会抹掉其明确的范围结论。

ReviewRecord / ReviewReuse / HandlingRecord 仍是数据库真源；查询按需生成投影，不向 ContentNode 写入可变通过标记。没有迁移或新的强制审核阶段。整稿 `overall_verdict` 只对准确选定的快照及导出使用已有最终审核投影；普通节点显示各标准、范围的判断，整体值保持 null，不把 null 解释为“不通过”。

## 查询契约

`read_review_status(snapshot_ref, target_ref=None, export_ref=None, offset=0, limit=20)` 向协调者、作者、局部审核者和原生最终 grader 开放。委派角色仍须服务端任务绑定。

- 默认清单包含快照、内容节点、需求，以及相应导出/渲染；另包含实际被审核过的其他清单内对象。需求对象可供调查“要求存在、内容却缺失”的情况，不要求每个需求单独调用审核。
- `target_ref` 可选择一个精确对象。`offset/limit` 对对象分页（最多 100），返回总数、已返回引用、继续偏移和本页未返回数量；单对象审核历史目前完整返回，尚未单独分页。
- `scopes` 按原被审对象、标准、范围、检查类型和成品身份分组。`judgment` 保留判定与对应证据、覆盖；`latest_execution` 单独展示该范围最近一次适用执行及其覆盖。既有 N 不会被后来 S、null、受阻或 handled 自动撤销；纠正需要既有显式纠正操作。
- 无当前记录显示 `not_started` 和空 scopes；`has_review_history` 区分从未审与只有历史记录。旧版、被纠正或已失效的记录留在 `review_history`，不提供当前正向覆盖。
- `needs_recheck` 表示存在 `recheck_candidates`，是历史适用性线索，并非代码指定必须执行的任务。候选由审核者决定如何调查；显式复用、独立来源变化和导出身份分别展示。历史候选不会覆盖新最终审核结论，既有 N 的保留规则仍成立。
- `handling_records` 独立显示各处理链及末端记录，不用“已处理”代替“已修复”。不同版本的处理引用单独列出。
- 查询不给出新的观察回执，不产生新 ReviewRecord，不切换当前交付、不触发其他智能体或模型调用。智能体仍需根据目标获取实际内容、来源或页面证据。
