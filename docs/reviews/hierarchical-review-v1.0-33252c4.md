## 确认发现

### R01 / P2：旧通过状态掩盖新增缺陷或未审核的新交付

位置：`src/report_agent/knowledge_state.py:52`、`src/report_agent/deep_runtime.py:652`、`src/report_agent/hierarchical_tools.py:156`。

分层状态投影直接返回缓存的 `report_status`，没有检查当前交付是否与已审版本一致，也不重新考虑新增反馈。`run_report` 遇到 `reviewed_draft` 又直接返回。

Main 用实际原生框架和离线脚本模型复现：初次 S 后保存同版本局部 N，实时 `review_summary` 已为 N，但项目仍为 `reviewed_draft`；再次运行的模型调用数为 0。再选择另一未审快照及导出，状态仍为 `reviewed_draft`，其交付目标与最终审核目标已经不同。

设计依据：§6 的判定聚合及 §8 的版本适用性；已确认缺陷不可被缓存结论覆盖，新版本不能自动继承通过。

影响和等级理由：影响分层报告恢复与对外状态的可靠性；历史记录尚完整，可通过明确标记待审和独立核对隔离，定为 P2。阻断“当前交付已经通过”的状态声明；不阻断隔离诊断。

最小变更：状态读取按当前快照/导出、适用审核和新增反馈计算；版本选择或相关反馈变化使缓存失效；快速返回前使用同一判定。临时措施：相关试验不依赖缓存标签，人工核对目标和最新反馈。

Main 处置：接受；由运行集成维护方在下一次交付恢复测试前修复，新增“通过后发现问题”和“通过后换稿”的回归。

### R02 / P2：整体通过遗漏独立的成品核查完成状态

位置：`src/report_agent/hierarchical_review.py:149`、`src/report_agent/content_models.py:130`、`src/report_agent/hierarchical_review.py:76`。

最终义务仅由各标准的 `delivery` 项构成，条目默认是内容审核。未独立核算导出保真和实际页面核查范围。Main 的原生框架复现仅调用 `read_context`，未读取导出、渲染或观察页面，也能保存整体 S 和 `reviewed_draft`；架构专家核对了这条路径。

设计依据：§6 规定必需检查未完成时整体暂无判定；§7 区分成品内容保真与页面呈现。这里确认的是义务遗漏，不是依据脚本模型判断真实模型是否会错误放行。

影响和等级理由：内容级结果可能被投影成完整成品通过；可限定为内容级试验或待审导出，定为 P2。阻断完整成品审核通过的声明。

最小变更：最终任务和聚合明确保留内容、导出保真、页面质量的实际覆盖与执行状态，欠执行时保留 null。仍由智能体决定方法、深度、复用和工具顺序；不加入强制逐页调用或固定多阶段流程。

Main 处置：接受；由审核契约维护方在真实成品验收前修复。临时将当前 S 限定解释为已记录内容义务的判定，不推定成品核验完成。

### R03 / P2：写权限只区分角色，无法区分实际委派任务

位置：`src/report_agent/hierarchical_tools.py:22`、`src/report_agent/deep_runtime.py:588`、`src/report_agent/content_store.py:165`。

全部 writer 使用固定 `content:writer` 和 `content-task:writer`；真实委派没有服务端目标/成果写范围。架构专家在临时库分别创建两组 writer 工具：A 保存章节节点，B 使用 A 的引用成功提交 v2。串行执行并未建立任务边界。

设计依据：§2、§5 与 C25：服务端绑定当前任务及成果所有者；调用工具不能扩张委派权限。

影响和等级理由：任务范围主要依赖提示词，不能强制保障分工成果所有权；可隔离为单一全报告生产任务，定为 P2。阻断依赖任务隔离的章节委派及“按任务控制写权限”的声明。

最小变更：服务端绑定真实生产任务、持续的所有者身份和授权成果范围，在提交时校验；恢复同一任务时维持身份连续性。

Main 处置：接受；由委派/权限维护方在扩展分任务写作前修复。临时仅使用单一全报告生产任务。

### R04 / P2：figure 图片来源可漏出冻结快照

位置：`src/report_agent/content_export.py:75`、`src/report_agent/content_export.py:95`。

figure 分支直接读取 `body.source_id`，未加入 `used_images`，绕过后续快照来源成员校验。代码专家用真实 PNG 复现：快照只含来源 `s`，figure 引用项目内另一图片来源 `fig`，仍成功嵌入和导出，结果为 `{"source_ids":["s"],"ok":true}`。

设计依据：§3 的完整采用闭包与 §7 的快照导出。原始文件哈希校验仍在；本轮没有确认“原件字节可被静默替换”，不扩大结论。

影响和等级理由：实际导出输入与快照来源清单不一致，依赖分析和审计不能覆盖图片；可在导出前补齐来源并重新冻结，定为 P2。阻断受影响图像报告的来源闭包完整验收，不阻断全部导出试验。

最小变更：figure 与 Markdown 图片统一校验来源成员及固定摘要。临时逐项核对 figure 来源已在快照清单。

Main 处置：接受；由导出维护方在图像报告主干验收前修复。

### R05 / P2：独立发现的资料无法保存为精确审核依赖

位置：`src/report_agent/content_store.py:282`、`src/report_agent/hierarchical_tools.py:174`。

审核提交中的引用，除同快照 Export/Render 外全部必须在作者快照内。代码专家读取快照外、项目内已保存的 SourceArtifact 后，将其加入审核 `dependency_refs`，被拒绝为 `REVIEW_VERSION_OUTSIDE_SNAPSHOT`。审核者也没有只读来源版本捕获入口。

设计依据：§2 允许独立查阅作者未选择的资料，§3/§6 要求审核依据有精确版本，§4 区分作者采用与审核后发现的依据。

影响和等级理由：仍可通过观察回执和文字反馈发现问题，但无法完整登记独立反证的类型化依赖；相关来源变更和审核复用缺少可靠关联。可保留回执并禁用相关复用，定为 P2。阻断“独立来源审核与版本依赖闭环完成”的声明。

最小变更：分开校验被审对象和审核依据。目标属于冻结快照；证据属于授权项目且固定版本即可。允许只读捕获来源版本并引用，不改写作者快照。

Main 处置：接受；由证据/审核存储维护方在下一次真实审核对比前修复。临时保存明确来源标识和原始读取回执，标注依赖未登记，禁止相关跨快照复用。

## 架构一致性与尚未完成的能力

独立架构审核检查到：公共/角色/任务提示与工具没有强制四层审核顺序；文本分析能力有界调用后返回；审核不能改写内容或标准；S/N/U/null 与转交状态分离。这些方向符合已确认的智能体原则，不需要因此重建整个系统。

- 快照唯一身份和冻结清单已存在，但缺稳定文档身份与明确前版快照链；当前版本隔离仍成立，修订谱系不完整。
