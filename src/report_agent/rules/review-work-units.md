This review uses the work-units-v1 planning contract. After the reconnaissance needed to identify the assigned scopes and available materials—and before the first verification or judgment tool call—declare the work units. You may continue reconnaissance afterward; do not wait for all evidence before declaring. Choose and revise the units and methods yourself; combine related standards where useful. This does not require a separate model turn for planning.

Both forms declare the same native todo list: the write_todos tool, or exactly one public JSON object {"review_plan":{"todos":[...]}} in the assistant message. They are alternative declarations, not two plans. When you declare and verify in the same response, use the public JSON form; a native write_todos call in that response is not guaranteed to be visible to the check before the verification tool runs. If both forms appear in one response, they must be identical; inconsistent declarations are rejected, not merged. The JSON object must be the entire assistant text content; ordinary explanatory prose is not parsed as a plan.

A verification todo that is a work unit carries content, status, and review_unit with assigned_scope_indexes, material_refs, material_needs, method, decision_conditions, and remaining_work. A verification note that is not a work unit may omit review_unit; it does not count toward scope coverage. Use only zero-based indexes from this task's saved review requirements; together the units must cover every assigned scope, including work awaiting clarification. One unit may cover several scopes, and a scope may appear in more than one unit. The structured fields, not content, carry the task/check IDs and versions for this contract; keep content a human-readable label and do not copy server scope IDs or version digests into it.

List exact, existing material versions available to this task; a listed ref is a plan, not a read receipt. If a needed material is not available, name it and its purpose in material_needs. State the planned method and the conditions for satisfaction, violation or missing required outcome, and unresolved limits, without inventing evidence or assuming a verdict. Update remaining_work when the unit changes; empty means no known remaining work.

The program binds units to this actor, task, snapshot, review basis and release. Do not supply or copy the server-generated _binding field. Reads, source/receipt capture, and render preparation may precede the declaration. A rejected declaration or action is not an observation and has not completed its check: correct it and retry, or record the check as unfinished—never as satisfied. Program validation is structural only (fields, scope coverage, material pool, binding); it does not prove the method is adequate, that the plan was followed, or that any check was performed. Plan structure and progress are intentions, not observations, saved review results or engineering acceptance.
