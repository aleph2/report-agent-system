## Design and increment

One reusable ADK execution mechanism. A coordinator may arrange and run authorized
outcome tasks serially; no creation of a fixed roster, no five-stage for-loop. The
capability map defines allowed output ownership, never mandatory task counts.
Coordinator tools cannot directly write purpose/material/draft/review results.
Execution tools run exactly one scoped task and return to the coordinator.

Purpose understanding is required for a submitted plan, not a mandatory purpose
model call. Operator-provided source-linked document-use statements and valid saved
results may be reused. A missing basis can lead to a purpose task. Model-selected
task kinds are checked against server policy; a worker cannot create another role
or submit a result owned by another role. Purpose/plan/material/draft/review records
are immutable, with input references. Review is bound to the exact draft version.

Implement outcome task persistence, result receipts, visible errors, targeted feedback,
human issue decisions, recovery and deterministic draft export. Add a small desktop
workbench exposing progress, errors, human issues, results and secondary logs. Sources
are synthetic manifests or already parsed input text; no OCR or raw-file ingestion.

Early reviewer advice adopted: permission dictionary is not workflow; outputs rather
than role-execution history enforce prerequisites; immutable records do not replace
write permissions; export never triggers an implicit agent pipeline. No role-union
permissions. Pending human wait policy remains undecided; unresolved issues cannot
be reported as resolved or converted to a reviewed result silently.

error and human issue visibility. Exports are drafts, not engineering sign-off.

engineering acceptance remain separate evidence requirements; no mock pass substitutes.
